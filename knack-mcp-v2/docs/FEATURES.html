knack-mcp-v2 — what it can do

An MCP server that gives an AI assistant working access to Knack apps: schema, records, files, fields, pages and views — with a safety guard around every view change.

At a glance

The short version, for a side-by-side comparison.

57tools in full mode
34tools in read-only mode
6access levels, opt-in per app
~8,500tokens for the whole catalogue (v1: ~10,600)
  • Transport: local stdio process (Node ≥ 20). Nothing hosted; the API key never leaves the developer's machine.
  • Authentication: Knack application ID + REST API key, against api.knack.com/v1. Keys live in a secrets file outside the repos, mapped by app key.
  • Multi-app: one folder per app under a root directory; the active app is chosen by key or inferred from the file being edited (knack_set_context).
  • Scope: not only records. It reads and writes fields and views (create, update, copy, move, reorder, delete) through the same builder endpoints the Knack Builder uses.
  • Offline fallback: cached schema.json, fieldMap.json, viewMap.json and a field-reference index are used when the API is unreachable, and are also exposed as MCP resources (knack://<AppKey>/schema, /fieldMap, /viewMap).
  • Human in the loop: any view change that would destroy a page is put to a person through MCP elicitation. A client that cannot prompt a human cannot cascade-delete.
  • KTL aware: finds, protects and edits KTL keywords in view titles/descriptions and field descriptions.
  • Token budget is a design constraint: one-sentence tool descriptions, mode parameters instead of near-duplicate tools, compact JSON, size caps with structural summaries on overflow.

Permission model

Set per app in schema/app.json. A level is advertised to the model only if at least one app opts in, and every call re-checks the selected app.

Level Enabled by Covers
read always Schema, records, files, views, analysis, snapshots, payload templates
write readonly: false Create/update records, upload assets, create/update/duplicate fields
delete allowDelete: true Delete records, delete fields
view allowViewMutation: true Create, update, reorder, copy, move views; append columns, action links, rules, links
view-delete allowViewMutation + allowDelete Delete a view
diagnostic allowDiagnostics: true Raw object / view payloads, live record shape verification
  • --readonly flag or KNACK_MCP_READONLY=1 pins the whole server read-only regardless of any app.json.
  • dataAccess read policy (optional, per app): allowedObjectKeys, allowedFieldKeys per object, redactedFieldKeys, maxRecordsPerQuery. Record tools, related-record lookups, aggregates, shape verification and seed CSV generation all honour it.

Safety features

Most of the code is here, not in the API calls. Every rule was measured against a live disposable app.

Cascade-delete guard

Knack destroys a page when a view update no longer carries the last link to it. Before every view change the server reads fresh metadata, works out which pages would lose their last link, and asks a human through MCP elicitation. No human available → the change is refused.

Automatic restore points

Every view change writes a snapshot to schema/snapshots/ first (creates and copies snapshot after). Version 3 snapshots keep page access: login roles and the profile → user-object map.

Merge, never blind PUT

knack_update_view and the five knack_add_* tools read the live definition themselves and send it back whole, so the caller never needs a full copy of the view and cannot drop what it did not know about.

Preview everything

previewOnly on view changes, dryRun on records and fields, confirm on record deletes. A preview sends nothing to Knack and writes nothing.

KTL keyword guard

A title or description edit that would silently drop a keyword is refused with KTL_KEYWORDS_WOULD_BE_DROPPED unless explicitly confirmed. keywordEdits adds or updates one keyword in place, siblings untouched.

Attributed field notes

Any field description written through the server is stamped _notes=<name> on <date>, preserved on later edits, re-attributed only on request.

Payload sanity checks

Page-shaped payloads sent as views are refused before reaching Knack; links that name no existing page come back as danglingLinks with a warning.

Audience change warnings

On a move or page transfer, the prompt names who can reach each page before and after: CHANGES, unchanged or UNKNOWN — verify in the builder.

Data read policy

Per-app allow-lists for objects and fields, redacted fields, and a per-query record cap — so an assistant can work on an app without seeing personal data.

Bounded responses

Upstream body cap (20 MB), tool response cap (256 KB, larger becomes a structural summary), attachment text cap (192 KB), batch concurrency cap (5, max 10).

Typical examples

What is asked in plain language, and the call(s) it turns into.

1. Pick the app from the file being edited

"I'm working in this file — which Knack app is this, and what can you change in it?" 
knack_set_context { "contextPath": "C:/KnackApps/Orders Portal/src/custom.js" }
knack_list_apps   {}

2. Look up a schema without opening the Builder

"What fields does Work Orders have, and what is it connected to?" 
knack_get_object             { "objectKey": "object_12" }
knack_get_object_connections { "objectKey": "object_12" }

3. Find records

"Show me the 50 most recent open work orders for customer Acme." 
knack_find_records {
  "objectKey": "object_12",
  "filters": { "match": "and", "rules": [
    { "field": "field_88", "operator": "is",       "value": "Open" },
    { "field": "field_91", "operator": "contains", "value": "Acme" } ] },
  "sortField": "field_66", "sortOrder": "desc", "rowsPerPage": 50
}

4. Totals without pulling the data into the conversation

"How many orders per month this year, by status, and the total amount?" 
knack_aggregate_records {
  "objectKey": "object_27",
  "filters": { "match": "and", "rules": [
    { "field": "field_310", "operator": "is during the current", "type": "year" } ] },
  "groupByFieldKeys": ["field_305"],
  "dateBucket": { "fieldKey": "field_310", "granularity": "month" },
  "metrics": [ { "type": "count" }, { "type": "sum", "fieldKey": "field_318" } ],
  "maxRecords": 10000
}
Only the aggregates come back, so the model never sees the rows.

5. Bulk update, rehearsed first

"Set these 40 records to Archived — show me what would happen before doing it." 
knack_update_records {
  "objectKey": "object_12",
  "records": [ { "recordId": "66f0…a1", "data": { "field_88": "Archived" } }, … ],
  "dryRun": true
}
Re-run with dryRun: false. Each record reports its own result; only HTTP 429 is retried.

6. Read an attachment

"Summarise the PDF spec attached to this record." 
knack_read_file { "objectKey": "object_40", "recordId": "66f0…b7", "fieldKey": "field_512" }

7. Add a column to a grid

"Add Due Date and the customer's phone number to the Open Orders grid, right after Status." 
knack_add_view_columns {
  "sceneKey": "scene_154", "viewKey": "view_617",
  "fieldKeys": ["field_93", "field_22"],
  "columnConnections": { "field_22": "field_91" },
  "insertAfterFieldKey": "field_88"
}
field_22 lives on the connected Customer object, reached through connection field_91.

8. Create a field

"Add a required multiple-choice Priority field to Work Orders, with a help text." 
knack_describe_field_shape { "fieldType": "multiple_choice" }
knack_create_field {
  "objectKey": "object_12", "name": "Priority", "type": "multiple_choice", "required": true,
  "format": "{\"type\":\"single\",\"options\":[\"Low\",\"Normal\",\"High\"],\"default\":\"Normal\"}",
  "description": "Drives the sort order of the shop-floor grid", "notedBy": "Norm"
}
Stored description: Drives the sort order of the shop-floor grid _notes=Norm on 2026-09-20

More complex examples

Multi-step jobs where the server's analysis and guard tools matter more than the API calls.

Impact analysis

A. "Can I delete this field?"

"Where is field_305 used? I want to remove it." 
knack_list_field_references { "fieldKey": "field_305", "groupByView": true }
knack_list_field_references { "fieldKey": "field_305", "classification": "viewRecordRule", "groupByView": true }
knack_search_emails         { "query": "field_305", "includeMessage": true }
Returns every view, filter, rule, record rule, alias and email template touching the field — the list the Builder does not give in one place.
View construction

B. Build a scoped grid from nothing

"On the Customer Details page, add a grid of that customer's open orders, newest first." 
knack_get_view_payload_template {
  "viewType": "grid", "objectKey": "object_12", "sceneKey": "scene_88",
  "title": "Open orders",
  "fieldKeys": ["field_60", "field_88", "field_66"],
  "connectionKey": "field_91", "relationshipType": "foreign",
  "parentSourceObject": "object_3", "parentSourceConnection": "field_91",
  "filters": "{\"match\":\"all\",\"rules\":[{\"field\":\"field_88\",\"operator\":\"is\",\"value\":\"Open\"}]}",
  "sort": "[{\"field\":\"field_66\",\"order\":\"desc\"}]",
  "noDataText": "No open orders"
}
→ review / edit the returned payload
knack_create_view { "sceneKey": "scene_88", "payload": "…" }
The template builds a valid source block and page layout; the create returns a snapshotPath so the new view exists on disk from minute one.
View reuse

C. Copy a grid to another page and keep its child pages shared

"Put a copy of the Orders grid on the Supervisor page, under the KPI view, with the same Edit and Details pages — don't duplicate them." 
knack_copy_view {
  "viewKey": "view_617", "targetSceneKey": "scene_201",
  "sharePages": true, "name": "Orders (Supervisor)",
  "insertAfterViewKey": "view_940"
}
Knack's own copy duplicates or drops link pages; sharePages: true re-creates the view from its definition so both grids link to the same pages. Ownership of the shared pages is handled so deleting the copy later cannot take them with it.
Page restructuring

D. Move a view safely

"Move the Orders grid from the Admin page to the Planner page. Tell me first what breaks and who will be able to see it." 
knack_list_page_referrers { "sceneKey": "scene_155", "includeDescendants": true }
knack_get_page_access     { "sceneKey": "scene_154" }
knack_get_page_access     { "sceneKey": "scene_201" }
knack_move_view { "sourceSceneKey": "scene_154", "targetSceneKey": "scene_201",
                  "viewKey": "view_617", "previewOnly": true }
→ then for real: snapshot written, human prompted if a child page would be orphaned
   or re-parented, with the audience before/after named in the prompt
Workflow

E. Add an "Approve" action link with rules

"Add an Approve button to the grid: only show it when Status is Pending, set Status to Approved and stamp the date." 
knack_add_action_link {
  "sceneKey": "scene_154", "viewKey": "view_617",
  "actionLinks": "[{\"link_text\":\"Approve\",\"action_rules\":[{\"link_text\":\"Approve\",
     \"criteria\":[{\"field\":\"field_88\",\"operator\":\"is\",\"value\":\"Pending\"}],
     \"record_rules\":[{\"action\":\"record\",\"criteria\":[],\"values\":[
        {\"field\":\"field_88\",\"type\":\"value\",\"value\":\"Approved\"},
        {\"field\":\"field_97\",\"type\":\"current_date\"}]}],
     \"submit_rules\":[{\"action\":\"message\",\"message\":\"Approved\",\"reload_show\":true}]}]}]",
  "previewOnly": true
}
Same pattern for form rules: knack_add_view_rules appends to rules.records / rules.submits without touching the rest.
KTL

F. Edit one KTL keyword without retyping the cluster

"On view_617, change the auto-refresh to 30 seconds and add _ts. Leave the other keywords alone." 
knack_search_ktl_keywords { "keyword": "_ar" }
knack_update_view {
  "sceneKey": "scene_154", "viewKey": "view_617",
  "keywordEdits": "{\"description\":{\"_ar\":\"30\",\"_ts\":null}}"
}
_ar is updated in place, _ts is appended to the trailing cluster. A plain description rewrite that lost a keyword would have been refused.
Data source

G. Same grid, different data source

"Make a copy of the Client Purchases grid, but showing purchases for all stores instead of only the store connected to the logged-in account." 
knack_plan_view_repoint { "viewKey": "view_112" }
→ RESCOPE keys: source.parent_source, source.connection_key — nothing else depends on them

knack_get_view_payload_template {
  "fromViewKey": "view_112", "sceneKey": "scene_76",
  "title": "Client Purchases - All Stores"
}
→ in the returned payload, remove from "source":
     parent_source, connection_key, relationship_type, authenticated_user
   (object, criteria, sort and limit stay)

knack_create_view { "sceneKey": "scene_76", "payload": "…" }
The Builder sets a view's data source when the view is created and offers no way to change it afterwards, so this normally means rebuilding the grid by hand. Here every column, width, grouping, sort, inline-edit setting and KTL keyword comes across. The "edit" link column keeps pointing at the same Edit Purchase page (shared, not duplicated), and because the listed object has not changed, every field, filter and sort stays valid. The reverse — narrowing an "all records" grid to the logged-in user's records — is the same three calls with those keys added instead of removed.
Refactoring

H. Re-point a view at a different connection

"This grid shows orders through the Customer connection; I need the same grid through the Site connection. What has to change?" 
knack_plan_view_repoint { "viewKey": "view_617", "includeScopedFields": true }
knack_get_view_payload_template { "fromViewKey": "view_617", "sceneKey": "scene_310" }
→ apply the listed rescope / retarget edits to the payload
knack_create_view { "sceneKey": "scene_310", "payload": "…" }
Onboarding & test data

I. Take over an app nobody documented

"I just inherited this app. Give me the full picture, tell me what looks wrong, and prepare test data for a sandbox copy." 
knack_app_deep_dive      { "includeScenes": true }
knack_analyze_data_model {}
knack_search_emails      {}
knack_generate_seed_csvs { "objectKeys": ["object_3", "object_12", "object_27"], "rowsPerObject": 6 }
Seed CSVs come out in import order with connection cells that match the parent rows' display values, so Knack's importer links them.
Custom code support

J. Check a JavaScript field map against the live schema

"Validate the field constants in this file — anything renamed, deleted or duplicated?" 
knack_validate_field_mapping      { "mappingObject": { "WO_STATUS": "field_88", "WO_CUSTOMER": "object_12.customer" } }
knack_check_duplicate_field_usage { "mappingObject": { … } }
knack_get_context_bundle { "objectKeys": ["object_12"], "viewKeys": ["view_617", "view_618"] }
Data migration

K. Consolidate a lookup table

"Merge this long list of category codes into a short one: create the new codes, re-link every record, show me counts before and after, then delete the old ones." 
knack_aggregate_records  → counts per old code (before)
knack_create_records     → the new codes           (dryRun, then real)
knack_find_records       → records per old code, paged
knack_update_records     → re-link, 100 per call
knack_aggregate_records  → counts per new code (after) — must reconcile
knack_list_field_references → filters and rules still naming old values
knack_delete_records     → preview, then "confirm": true

What it does not do

For an honest comparison — none of these have a tool today.

  • Pages: no rename, delete or access-settings change of a page, and no top-level page creation. A new page can only be created as the child of a view link (knack_add_page_link_column); login and roles are read, not written.
  • View payload templates cover grid/table, form, details and list. Other view types (menu, rich text, search, calendar, map, report/chart…) can be created from a hand-built payload or a clone, not from a template.
  • Tasks / Flows, app-level settings, themes, custom JS/CSS: not read, not written.
  • User accounts and roles: reachable only as records of the account objects; no role management.
  • Import / export jobs, record history, app copies: none.
  • Aggregates: count and sum only (no average, min, max), computed client-side over a capped scan.
  • Hosting and auth: local stdio only — no remote endpoint, no OAuth, no per-user identity. Everything runs as the app's REST API key, so Knack-side page/role security does not apply; the server's own dataAccess policy is the substitute.
  • View-based API (login as a user, page-scoped requests): not used.
The view and field tools rely on builder endpoints under api.knack.com/v1 (/objects/…/fields, /scenes/…/views, /copyview, /views/sort) that are not part of Knack's published API. Their behaviour was established by measurement on a disposable test app. Two findings shape most of the safety code: a view PUT replaces the whole definition instead of patching it, and a child page is destroyed when the definition Knack receives no longer carries the last link to it. On documented endpoints with patch semantics, most of that guard code would not be needed.

Basis of comparison

What the side-by-side table below assumes about the Knack MCP Server.

Reading it: Knack's server is for standing up a backend — apps, tables, fields, roles — for a frontend built elsewhere. knack-mcp-v2 is for maintaining existing Knack apps, including their pages and views, safely. They are complementary: the official one creates what this one cannot (apps, tables, DAC), and this one edits what the official one does not touch (views, rules, layout).
